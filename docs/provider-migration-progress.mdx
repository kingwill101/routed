# Typed provider migration

Routed's current configuration model is intentionally code-first. The old
configuration loader, application YAML files, provider manifest, dot-notation
overrides, and configuration reload events are not part of the supported API.

## Current contract

- Each feature provider accepts one typed configuration object.
- Configuration objects may implement `ValidatableConfiguration`.
- `Engine` validates and publishes provider configuration through `ConfigStore`
  before booting providers.
- Deployment environment and secrets enter through `RuntimeContext`.
- `EngineOpt` is reserved for wiring (`withMiddleware`, `withService`) rather
  than feature configuration.
- Provider selection is explicit in `Engine(providers: ...)` or through the
  official `Engine.builtins` catalogue.

Examples of the supported shape:

```dart
final engine = await Engine.create(
  runtime: runtime,
  providers: [
    CoreServiceProvider(EngineConfig()),
    RoutingServiceProvider(const RoutingConfig()),
    RoutedSecurityProvider(RoutedSecurityConfig()),
    RoutedStorageProvider(
      StorageConfig(
        disks: {
          'local': const LocalStorageDiskConfig(root: 'storage/app'),
        },
      ),
    ),
  ],
);
```

The detailed provider pages and package READMEs are being kept aligned with
these constructors. When a provider needs an application-owned runtime object,
that object is passed through the provider's typed configuration or an explicit
typed service binding owned by the adapter package.

## Compatibility decision

This is a deliberate breaking release. There is no compatibility layer that
silently translates removed YAML keys or string paths. Applications should
rewrite configuration at the provider boundary so invalid setup fails during
startup instead of being accepted and interpreted later.
