Auth endpoint security contract

This page is the public HTTP security contract for Routed authentication. It describes the routes an application receives from its selected providers and server plugins. It does not describe storage tables or internal implementation types.

The default auth base path is /auth. Paths in the matrices below are relative to that base path unless they begin with /.well-known/. Applications may choose another base path through their typed deployment or AuthOptions.

Use the public Dart entrypoints:

import 'package:routed_auth/routed_auth.dart';
import 'package:server_auth/server_auth.dart';

See the routed_auth API, the server_auth API, the Routed OAuth example, and the framework-neutral auth example.

How to read the matrix​

  • Public means no existing Routed identity is required. A one-time code, passkey assertion, OAuth client credential, bearer token, or API key may still be required by that operation.
  • Session means the configured server-session or JWT identity is required. Organization and Admin operations apply their own permission checks after authentication.
  • Browser Origin means Routed validates an exact same or explicitly trusted Origin, rejects untrusted cross-site Fetch Metadata, and applies the configured Referer and content-type policy. Native clients without browser headers remain supported unless requireOrigin is enabled.
  • CSRF means the request must present the token obtained from GET /csrf through X-CSRF-Token or _csrf. The typed client transport fetches, caches, and retries this token automatically for mutation methods that use its mutate operation.
  • Context key means the endpoint contributes no user identifier. The application limiter can still use the trusted client address, method, path, operation, and provider namespace.

Every configured limiter receives a non-secret namespaced operation. Core operations use core.*; plugin operations use the plugin namespace shown in the matrix. Passwords, OTPs, captcha tokens, OAuth codes, bearer tokens, and API keys are never limiter identifiers. A blocked request returns 429 with Retry-After.

Core providers and account routes​

These routes are supplied by Routed auth itself. Provider-specific sign-in and registration behavior exists only for providers included in AuthOptions.providers.

Username​

OperationsAuthenticationBrowser / CSRFRate-limit namespace and keyResult
POST /username/registerPublicBrowser Origin; no CSRFusername.registration; canonical usernameCreates the credential and issues the configured identity, or returns a 2FA challenge when policy requires it.
POST /username/sign-inPublicBrowser Origin; no CSRFusername.sign_in; canonical username or email selected by the typed identifier policyIssues the configured identity, or returns a 2FA challenge. Ambiguous identifiers are rejected.
POST /username/changeSessionBrowser Origin + CSRFusername.change; current user IDAtomically reserves the normalized target while updating the credential and public user projection. Replaying the same target is idempotent; conflicts and unavailable accounts use a generic failure.
POST /username/removeSessionBrowser Origin + CSRFusername.remove; current user IDAtomically removes the username only when the authoritative authentication-method inventory proves another usable method remains. Replays are idempotent and unsupported mixed-store topologies fail closed.

Selecting UsernamePlugin requires the root auth store to implement AuthUsernameStore. Durable adapters own the full transaction and identifier uniqueness constraint; Routed does not fall back to a lookup/remove/write sequence.

Captcha and breached-password policy​

These plugins add no endpoints.

  • CaptchaPlugin gates credentials and username sign-in/registration. It receives a bounded captcha token only at the verifier boundary and always returns captcha_failed for malformed, rejected, timed-out, replayed, or provider-failed verification. AuthCaptchaClientPlugin adds captcha-aware credentials methods to a selected client.
  • BreachedPasswordPlugin gates credentials and username registration, password reset, and authenticated password change according to its typed options. A breached password and lookup failure both return password_rejected. It adds no client API because no extra client field is required.

Session and body-token behavior​

Every successful auth-producing operation goes through the host-owned session path, including plugin sign-ins and 2FA completion. This applies account policy, callbacks, session events, and the configured strategy consistently.

Deployment strategyCookieSuccessful JSON body
Server sessionSecure/HttpOnly in production; server-side record is authoritativeSafe user/session fields; never the raw session cookie or stored token digest.
JWT APISecure/HttpOnly JWT cookieThe JWT is omitted by default. It appears as token only when exposeJwtTokenInSessionResponse is explicitly enabled.
API-key serviceAPI-key middleware does not create a cookieKey exchange, when enabled, produces a normal server session. Lifecycle responses never echo an existing raw API key.

A successful redirect carries the cookie but no JSON body. The shared AuthClientTransport stores response cookies; bearer clients may copy an explicitly exposed JWT into setBearerToken.

Public errors​

Expected failures use bounded lowercase codes in an {error: ...} JSON body. Unexpected plugin failures become auth_request_failed; provider exceptions, stack traces, paths, tokens, and credentials are not returned. Authentication and authorization failures generally use 401, browser or CSRF rejection uses 403, malformed requests use 400, an unknown provider uses 404, and rate limits use 429 with Retry-After. Protocol endpoints may use their stable OAuth/device error codes.

Account-enumeration boundaries deliberately collapse detail. Password-reset requests return the same accepted result for known and unknown emails, and OTP delivery responses do not reveal stored codes.

Compose server and client plugins separately​

The server and client are intentionally not one "god client". Add only the server capabilities the application exposes, then independently select only the client APIs each frontend or service uses:

final phone = PhoneNumberPlugin<EngineContext>(
  sendCode: sendPhoneCode,
  codeHashKey: phoneCodeHashKey,
);
final passkeyProvider = WebAuthnProvider(
  getUserInfo: resolvePasskeyUser,
  getRelyingParty: resolveRelyingParty,
);
final passkeys = WebAuthnPlugin<EngineContext>(
  provider: passkeyProvider,
);

final deployment = AuthDeploymentPresets.secureSessionProduction<EngineContext>(
  store: authStore,
  providers: [CredentialsProvider(), passkeyProvider],
  plugins: [phone, passkeys],
  boundary: productionBoundary,
  lifecycleDelivery: lifecycleDelivery,
  rateLimiter: rateLimiter,
  requireVerifiedEmail: true,
);

const phoneClientPlugin = AuthPhoneNumberClientPlugin();
final client = AuthClient(
  baseUrl: Uri.parse('https://api.example.com'),
  plugins: const [phoneClientPlugin],
);
final phoneClient = client.plugins.use(phoneClientPlugin);
await phoneClient.sendCode(phoneNumber: '+18765551234');
final session = await phoneClient.verifyCode(
  phoneNumber: '+18765551234',
  code: codeFromSms,
);

The deployment's authStore must implement AuthPhoneNumberBackend; the plugin does not accept a side store. Its transaction persists only keyed code digests and owns issuance replay binding, bounded attempts/lockout, expiry, one-time consumption, user/phone binding, and deletion cleanup. SMS delivery, callbacks, and Routed session/cookie issuance are explicit postcommit boundaries.

Installing WebAuthnPlugin on the server does not add passkey methods to this phone-only client. Add AuthWebAuthnClientPlugin only to clients that perform passkey ceremonies. The same pairing applies to credentials, providers, sessions, OAuth, magic links, email OTP, anonymous users, username, 2FA, API keys, accounts/passwords, organizations, Admin, and device authorization.

Typed deployment presets​

PresetIntended boundaryIdentity strategy
localDevelopmentLocal HTTP/tests with explicitly ephemeral storageServer session with development cookie settings.
secureSessionProductionBrowser application with durable storage, exact HTTPS origins, explicit proxy policy, lifecycle delivery, and rate limitingDurable server session.
jwtApiProductionAPI/mobile clients with durable storage and explicit issuer/audience/signing choicesJWT cookie; body token exposure is an explicit required choice.
serviceApiKeyProductionService clients with durable auth/API-key stores and an explicit exchange choiceAPI-key request identity plus optional server-session exchange.

For Routed, construct AuthDeployment<EngineContext>, add deployment.serviceProvider() to the engine, create the engine with deployment.engineConfig(), call deployment.bindTo(engine), and then initialize. A deployment for another request-context type cannot be silently bound to Routed.
