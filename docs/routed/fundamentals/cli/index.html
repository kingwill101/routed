Routed CLI Reference

The routed_cli package ships project scaffolding, a hot-reload dev server, route/spec inspection utilities, and deployment helpers. Install it as a development dependency or activate it globally:

dart pub add --dev routed_cli
# or: dart pub global activate routed_cli

Run commands with dart run routed_cli <command> [...]. Add --verbose to surface extra debug output.

Choosing a Dart executable: The CLI honours the first set environment variable in ROUTED_CLI_DART, DART_BIN, or DART_PATH. Set one of these when you manage multiple SDKs (for example, with FVM) so every command launches the intended runtime.

create​

dart run routed_cli create --name my_app [--output <dir>] [--force]

Scaffolds a Routed project with bin/server.dart, typed provider setup, README, analysis options, and storage directories. It does not generate an application configuration directory or .env file.

  • --name/-n – project & package name (required when scaffolding into the current directory).
  • --output/-o – destination directory (defaults to .).
  • --template/-t – template to use (basic, api, web, or fullstack).
  • --force/-f – overwrite conflicting files.

After generating files, create automatically runs dart pub get using the resolved Dart executable. If dependency resolution fails the CLI prints the exit code and keeps the "Next steps" list so you can retry manually.

dev​

dart run routed_cli dev [-e bin/server.dart] [-H 127.0.0.1] [-p 8080]

Launches a development server with hot-reload support. Highlights:

  • Resolves the correct Dart binary (respecting the environment overrides above) and enables the VM service.
  • Generates a bootstrap that wires in hotreloader so file changes trigger reloads.
  • Restarts the process automatically when --no-bootstrap is used.
  • Accepts additional flags: --bootstrap-path, --install-missing/--no-install-missing, --no-warn-missing, and --watch for custom directories.
FlagAbbreviationDefaultDescription
--entry-ebin/server.dartEntrypoint file to run in development
--host-H127.0.0.1The host to bind
--port-p8080The port to bind
--bootstrap/--no-bootstraptrueGenerate and run a hotreloader bootstrap
--bootstrap-path(auto)Custom path for the generated bootstrap file
--install-missing/--no-install-missingtrueAuto-install hotreloader if missing
--no-warn-missingfalseSuppress warning when hotreloader is missing
--watch[]Additional directories or files to watch (repeatable)

Use this during development; fall back to dart run bin/server.dart for single runs or CI pipelines. If you see "Entry file not found" errors, pass -e to point at your server file.

deploy​

Build and deploy the application to a supported edge or serverless target:

dart run routed_cli deploy \
  --target cloudflare|netlify|vercel \
  [--entry package:my_app/app.dart] \
  [--name <deployment-name>] \
  [--dry-run]

The command locates the project from its pubspec.yaml, ensures the routed_node adapter is available, compiles the Dart entrypoint to JavaScript, and then invokes the target's official CLI through npx. Your entrypoint must export a createEngine() function. If omitted, the command uses the project's package:<package-name>/app.dart entrypoint.

Targets​

TargetRuntime/outputDeployment behavior
CloudflareWorker with nodejs_compatWrites a Wrangler config under .dart_tool/routed/deploy/cloudflare and runs wrangler deploy.
NetlifyEdge FunctionStages a netlify.toml and edge-function bundle, then runs netlify deploy --prod.
VercelNode.js function or Edge FunctionWrites a prebuilt Vercel output bundle and runs vercel deploy --prebuilt.

Vercel defaults to the Node.js runtime. Select the Edge runtime explicitly:

dart run routed_cli deploy \
  --target vercel \
  --runtime edge \
  --name my-routed-app

Use the Node.js runtime when the application needs Node-specific behavior, including the WebSocket upgrade path. The Edge runtime is fetch-based and is intended for handlers that fit the edge runtime's API constraints.

Cloudflare binding flags map directly to Wrangler configuration:

dart run routed_cli deploy --target cloudflare \
  --d1 DB=app-db:YOUR_DATABASE_ID \
  --durable-object COUNTER=Counter \
  --container APP=AppContainer\|./Dockerfile\|8080\|3 \
  --r2 FILES=app-files \
  --queue EVENTS=app-events \
  --service PROFILE_API=profile-api \
  --workflow BILLING=billing-workflow:BillingWorkflow:billing-worker \
  --secrets-store PAYMENTS_KEY=STORE_ID:PAYMENTS_API_KEY

The generated Worker exposes D1, Durable Objects, Container, R2, Queue, Worker service, Workflow, and Secrets Store bindings through package:routed_node/cloudflare.dart. --container also emits the Container Durable Object configuration and a forwarding class for its default port. Workflow classes hosted in another Worker should include the optional SCRIPT_NAME; locally authored Workflow entrypoints still need their own Cloudflare Workflow class export.

Dry runs and credentials​

--dry-run compiles the application and validates the generated deployment bundle without publishing it. Cloudflare also passes --dry-run to Wrangler; Netlify and Vercel stop after generating their local deployment artifacts.

The command does not create or upload application secrets. Authenticate with the target CLI before deploying and configure environment variables or secrets through that provider. For Cloudflare, --keep-vars preserves variables already configured in the Worker dashboard:

dart run routed_cli deploy \
  --target cloudflare \
  --name my-routed-worker \
  --keep-vars

The Cloudflare compatibility date defaults to the current date; set it explicitly for reproducible deployments:

dart run routed_cli deploy \
  --target cloudflare \
  --compatibility-date 2026-08-15 \
  --dry-run

If a deployment fails, fix the reported build or provider-CLI error and rerun the command. Cloudflare and Vercel keep their generated artifacts under the project's build directories for inspection; Netlify cleans its temporary staging directory after the command exits. Run dart pub get manually if the CLI added routed_node but dependency resolution was interrupted.

routes​

dart run routed_cli routes [--format table|json] [--entry tool/spec_manifest.dart]

Prints the HTTP and WebSocket routes for your application. The loader tries lib/app.dart (expecting a createEngine() function) and falls back to tool/spec_manifest.dart, or you can point to a custom entry. Use --format json together with --no-pretty when parsing from scripts.

openapi generate​

dart run routed_cli openapi generate
# legacy aliases:
dart run routed_cli openapi:generate
dart run routed_cli spec

Writes the runtime route graph as JSON to disk. This manifest is the input to the OpenAPI build-runner step and is also useful for documentation, contract tests, or code generators. The CLI ensures parent directories exist before writing.

FlagDefaultDescription
--entry(auto)Dart entrypoint that prints a route manifest as JSON
--output.dart_tool/routed/route_manifest.jsonTarget path for the generated manifest
--pretty/--no-prettytruePretty-print the JSON output

Build-time OpenAPI output​

cd examples/openapi_demo
dart run routed_cli openapi generate
dart run build_runner build --delete-conflicting-outputs

The first command executes the application engine and writes .dart_tool/routed/route_manifest.json. The routed_openapi_builder build-runner builder then enriches that runtime manifest and writes lib/generated/openapi.json plus lib/generated/openapi_controller.g.dart. Fluent metadata such as .summary(...), .tags(...), and .responseSchema(...) flows into the generated spec.

stimulus:install​

dart run routed_cli stimulus:install [--force]

Scaffolds Stimulus (Hotwire) application boilerplate and a sample controller into public/js/. Currently supports --mode cdn (the default), which generates ES modules that import Stimulus from a CDN.

Generated files:

  • public/js/stimulus.js – module entry point
  • public/js/controllers/application.js – Stimulus application setup
  • public/js/controllers/index.js – controller registration
  • public/js/controllers/hello_controller.js – sample controller

After scaffolding, include <script type="module" src="/js/stimulus.js"></script> in your HTML layout and attach controllers with data-controller attributes.

provider:driver​

dart run routed_cli provider:driver <type> <name>
dart run routed_cli provider:driver --type storage my_driver

Generates a starter file for a custom storage, cache, or session driver. The type argument selects the driver category (storage, cache, or session) and name is the driver identifier.

FlagAbbreviationDefaultDescription
--type-tstorageDriver category: storage, cache, or session
--output-olib/drivers/<type>Directory where the driver file is written
--force-ffalseOverwrite the target file if it exists

provider:list​

Lists provider registrations available to the current package. Provider configuration is supplied in Dart, so this command is an inventory tool rather than a manifest editor:

dart run routed_cli provider:list

Project-defined commands​

Every scaffold now includes lib/commands.dart exposing a buildProjectCommands() hook. Return one or more Command<void> instances and the Routed CLI will load them automatically when you run commands from inside the project. Project commands are listed under a "Project" section in dart run routed_cli --help alongside the built-ins.

lib/commands.dart
import 'dart:async';
import 'package:args/command_runner.dart';

class QueueWorkCommand extends Command<void> {
  @override
  String get name => 'queue:work';

  @override
  String get description => 'Run the queue worker for the selected queue.';

  QueueWorkCommand() {
    argParser.addOption('queue', defaultsTo: 'default');
  }

  @override
  Future<void> run() async {
    final target = argResults?.option('queue') ?? 'default';
    // Insert your worker startup logic here.
    print('Starting worker for $target');
  }
}

FutureOr<List<Command<void>>> buildProjectCommands() => [QueueWorkCommand()];

If a project command reuses a built-in name (or alias) the CLI exits with a descriptive conflict so you can pick a different identifier. Use this hook for queue workers, seeders, diagnostic scripts, and other project automation.

Provider-defined commands​

Providers can register CLI commands so every app that includes the provider automatically gains the associated tooling. Register commands with ProviderCommandRegistry and return a factory so the CLI can instantiate them only when it builds the command list.

lib/providers/my_provider.dart
import 'package:args/command_runner.dart';
import 'package:routed_cli/routed_cli.dart';
import 'package:routed/routed.dart';

class MyProviderCommand extends Command<void> {
  @override
  String get name => 'my:task';

  @override
  String get description => 'Run provider maintenance.';

  @override
  Future<void> run() async {
    // command logic
  }
}

class MyProvider extends ServiceProvider {
  @override
  void register(Container container) {
    ProviderCommandRegistry.instance.register(
      'my:task',
      factory: () => MyProviderCommand(),
      description: 'Provider maintenance command',
    );
  }
}

Provider commands are loaded alongside built-ins and project commands. If a provider command conflicts with an existing name or alias the CLI exits with a usage error so you can rename it.

For artisanal runners, use ProviderArtisanalCommandRegistry to expose provider command factories to application-specific tooling.

Troubleshooting​

  • dart pub get failures: The create command forwards the resolver's exit code. Fix dependency constraints, then rerun the command or execute dart pub get manually.
  • Hot reload not available: The dev server installs hotreloader automatically when the project contains a pubspec.yaml. Pass --no-install-missing to skip installation or --no-bootstrap to disable the bootstrap entirely.
  • Wrong Dart SDK: Set ROUTED_CLI_DART (or DART_BIN / DART_PATH) to a specific SDK path before running CLI commands.
