# Typed configuration

Routed configuration is Dart code. Provider configuration is constructed with
typed values, validated before startup, and exposed through an immutable
`ConfigStore`. There is no application YAML, `.env` loader, dot-notation map,
provider manifest, or runtime configuration reload in the current API.

## Compose providers

Each provider owns its configuration type. Register the providers your server
uses and pass each configuration to its provider:

```dart
import 'package:routed/routed.dart';

Future<Engine> buildEngine(RuntimeContext runtime) async {
  return Engine.create(
    runtime: runtime,
    providers: [
      CoreServiceProvider(
        EngineConfig(
          security: EngineSecurityFeatures(
            maxRequestSize: 10 * 1024 * 1024,
            cors: CorsConfig(
              enabled: true,
              allowedOrigins: ['https://app.example.com'],
            ),
          ),
          http2: const Http2Config(enabled: true),
        ),
      ),
      RoutingServiceProvider(
        const RoutingConfig(
          redirectTrailingSlash: false,
          handleMethodNotAllowed: true,
        ),
      ),
      UploadsServiceProvider(
        MultipartConfig(
          maxFileSize: 20 * 1024 * 1024,
          allowedExtensions: {'jpg', 'png', 'pdf'},
        ),
      ),
    ],
  );
}
```

Feature packages follow the same pattern. For example, use
`LoggingServiceProvider(LoggingConfig(...))`,
`RoutedSecurityProvider(RoutedSecurityConfig(...))`,
`RoutedStorageProvider(configuration: StorageConfig(...))`, and
`ViewServiceProvider(RoutedViewConfig(...))` when those plugins are needed.

The provider list is deliberately explicit. Importing a package does not turn
on a feature, and a provider cannot be enabled by changing a string in a
manifest.

## Environment and secrets

Deployment-specific values are supplied by the host as typed runtime input.
They are separate from portable application configuration:

```dart
final runtime = RuntimeContext(
  environment: RuntimeEnvironment({
    'APP_ENV': 'production',
    'PUBLIC_ORIGIN': 'https://app.example.com',
  }),
  secrets: RuntimeSecrets({
    'JWT_SECRET': jwtSecretFromPlatform,
  }),
);

final origin = runtime.environment.requiredString('PUBLIC_ORIGIN');
final jwtSecret = runtime.secrets.requiredString('JWT_SECRET');
```

Providers that need host bindings receive them through `RuntimeContext` rather
than converting JavaScript, Cloudflare, or `dart:io` values into maps.

## Looking up configuration

Use the type you registered. A request context and the engine both expose the
same immutable store:

```dart
engine.get('/health', (ctx) {
  final core = ctx.config<EngineConfig>();
  final routing = ctx.config<RoutingConfig>();
  return ctx.json({
    'maxRequestSize': core.security.maxRequestSize,
    'redirectTrailingSlash': routing.redirectTrailingSlash,
  });
});

final logging = engine.configStore.get<LoggingConfig>();
```

Unknown configuration types fail clearly. There is no fallback value for a
misspelled string key because the type is the lookup contract.

## Validation and startup

Typed providers validate their configuration before any provider `boot` method
runs. All discovered issues are returned together:

```dart
try {
  await engine.initialize();
} on ConfigValidationException catch (error) {
  for (final issue in error.issues) {
    stderr.writeln(issue);
  }
  rethrow;
}
```

Configuration is fixed after initialization. To change configuration, build a
new engine with a new provider composition. This keeps startup behavior
deterministic and prevents a file watcher or late map mutation from changing
provider state under live requests.

## Testing

Tests use the same provider constructors as production:

```dart
final engine = Engine(
  providers: [
    CoreServiceProvider(
      EngineConfig(fileSystem: MemoryFileSystem()),
    ),
    RoutingServiceProvider(),
  ],
);
await engine.initialize();

expect(
  engine.configStore.get<EngineConfig>().fileSystem,
  isA<MemoryFileSystem>(),
);
```

This makes test configuration compile-checked and keeps tests aligned with
the code that runs in production.
