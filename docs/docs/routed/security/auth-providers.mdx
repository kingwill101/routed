# Auth Providers & Adapters

OAuth providers are configured with typed option classes and passed through
`AuthOptions`. Secrets should come from `RuntimeSecrets` or another deployment
secret store.

## Built-in providers

`routed_auth` includes Google, Discord, Twitter/X, Facebook, Microsoft Entra,
Apple, GitLab, Dropbox, Slack, LinkedIn, Spotify, Twitch, and Telegram
providers. Each provider has a typed options class, for example
`GoogleProviderOptions`.

```dart
import 'package:routed/routed.dart';

final engine = Engine(
  providers: [
    ...Engine.defaultProviders,
    AuthServiceProvider(),
  ],
);

engine.container.instance<AuthOptions<EngineContext>>(
  AuthOptions<EngineContext>(
    providers: [
      googleProvider(
        GoogleProviderOptions(
          clientId: runtime.secrets.requiredString('GOOGLE_CLIENT_ID'),
          clientSecret: runtime.secrets.requiredString('GOOGLE_CLIENT_SECRET'),
          redirectUri: 'https://example.com/auth/callback/google',
        ),
      ),
      discordProvider(
        DiscordProviderOptions(
          clientId: runtime.secrets.requiredString('DISCORD_CLIENT_ID'),
          clientSecret: runtime.secrets.requiredString('DISCORD_CLIENT_SECRET'),
          redirectUri: 'https://example.com/auth/callback/discord',
        ),
      ),
    ],
  ),
);

await engine.initialize();
```

Provider registration helpers are not needed for auth providers. Construct the
typed provider options you need and pass the resulting provider instances in
the `AuthOptions.providers` list.

## Typed profiles

Provider profiles expose typed fields after the OAuth callback:

```dart
final profile = GoogleProfile.fromJson(rawData);
print(profile.email);
print(profile.name);
print(profile.emailVerified);
```

Validate provider claims before persisting an account and normalize the
provider subject as the stable external identifier.

## Custom user-info requests

Some providers require a POST request or custom headers for user info:

```dart
import 'dart:convert';

final provider = OAuthProvider<MyProfile>(
  id: 'custom',
  name: 'Custom Provider',
  clientId: clientId,
  clientSecret: clientSecret,
  authorizationEndpoint: Uri.parse('https://api.example.com/oauth/authorize'),
  tokenEndpoint: Uri.parse('https://api.example.com/oauth/token'),
  userInfoEndpoint: Uri.parse('https://api.example.com/userinfo'),
  redirectUri: redirectUri,
  userInfoRequest: (token, httpClient, endpoint) async {
    final response = await httpClient.post(
      endpoint,
      headers: {
        'Authorization': 'Bearer ${token.accessToken}',
        'Content-Type': 'application/json',
      },
    );
    return jsonDecode(response.body) as Map<String, dynamic>;
  },
  profileParser: MyProfile.fromJson,
);
```

Use the exact callback and profile types from `server_auth` for the custom
provider implementation.

## Custom adapters

Implement `AuthAdapter` when users, accounts, sessions, or verification tokens
need durable storage. Keep persistence behind the adapter so provider callbacks
do not access a database directly. Add failure handling and unique constraints
for provider subject plus provider ID.

## Security notes

- Keep client secrets in `RuntimeSecrets`.
- Validate OAuth state, PKCE, and nonce values through the built-in auth routes.
- Restrict redirect URIs to registered origins.
- Treat provider profile fields as untrusted input.
- Return generic callback errors and log provider details server-side.
