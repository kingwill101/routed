# Rate limiting design notes

The rate-limit implementation is split into a framework-agnostic runtime and a
small Routed adapter:

| Component | Responsibility |
| --- | --- |
| `server_rate_limit` | Policy specs, algorithms, key resolvers, backends, and outcomes. |
| `routed_rate_limit` | Typed `RateLimitConfig`, container binding, and request-context helpers. |
| `routed_cache` / `server_cache` | Cache stores and repositories used by a cache-backed limiter. |
| Application code | Chooses policies, middleware placement, failure response, and runtime inputs. |

## Build policies in Dart

Policies are compiled from typed `RateLimitPolicySpec` values:

```dart
final policies = compileRateLimitPolicies(
  specs: [
    RateLimitPolicySpec(
      name: 'api-ip',
      match: '/api/**',
      method: null,
      strategy: RateLimitStrategy.tokenBucket,
      capacity: 100,
      interval: const Duration(minutes: 1),
      window: const Duration(minutes: 1),
      period: const Duration(days: 1),
      burstMultiplier: 2,
      key: const RateLimitKeySpec.ip(),
    ),
  ],
  backend: backend,
  defaultFailover: RateLimitFailoverMode.allow,
);
```

The runtime supports token buckets, sliding windows, and rolling quotas. Key
resolvers include client IP, a request header, and custom Dart callbacks.

## Integration boundaries

- Put the limiter after authentication when the key uses an authenticated
  identity.
- Put it before expensive handlers and before response compression.
- Choose `allow`, `block`, or `local` failover deliberately for the resource.
- Use a shared repository for limits that must be consistent across instances.
- Treat `RateLimitOutcome` as application data and choose the response shape in
  the route or middleware.

`RateLimitService` publishes allowed and blocked callbacks, and the Routed
adapter exposes the service through `ctx.checkRateLimit`. The adapter does not
silently install policy enforcement for every route.

See [Rate limiting](/docs/routed/security/rate-limit) for a complete setup.
